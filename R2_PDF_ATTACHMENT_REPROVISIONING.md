# Re-provisioning: PDF attachment upload on unlock requests

**Status as of this writing: reason-only.** The DEO-side "Request Unlock" form (Milestone 28,
see ROADMAP.md and CLAUDE.md's "DEO self-service unlock requests" section) has no PDF-attachment
file input, and the admin `/admin/unlock-requests` table has no Attachment column, right now.
Not because the feature was cut — the schema and both backend routes are fully built and
untouched; the admin PDF-preview modal (`PdfPreviewModal.tsx`) exists but isn't wired into the
admin page. It's off because R2 requires a payment method on file to enable at the
Cloudflare-account level, even for free-tier usage, and that hadn't been set up yet at build
time — and once it was clear attachments couldn't work yet, the now-permanently-empty Attachment
column and its `hasAttachment: false` audit metadata were removed as dead UI rather than left
sitting there unused.

**The `r2_buckets` binding in `api/wrangler.jsonc` is currently commented out**, not just
unused — `wrangler deploy` hard-fails the *entire* Worker deploy with `[code: 10042]` if this
binding is present in config while the bucket doesn't exist in the account (discovered the hard
way: it silently broke the API deploy job for a full push while the Frontend Pages deploy
succeeded, leaving production briefly serving new unlock-request UI against an API that hadn't
actually picked up the matching routes). Re-enabling the binding is step 1 below, not optional.

This document is the complete, self-contained checklist to turn it back on — no need to re-read
the whole codebase or re-derive what's missing. Follow it top to bottom.

### 3. Backend route — `POST /api/deo/request-unlock` (`api/app/api/deo/request-unlock/route.ts`)

Already reads `FormData`, already validates and stores an attachment if one is present — this
route does not care whether the DEO UI ever sends a file. Full logic already live:

```ts
const PDF_MAX_BYTES = 2 * 1024 * 1024;
const PDF_MAGIC = [0x25, 0x50, 0x44, 0x46, 0x2d]; // %PDF-

async function isPdf(buf: ArrayBuffer): Promise<boolean> {
  const head = new Uint8Array(buf.slice(0, PDF_MAGIC.length));
  return PDF_MAGIC.every((b, i) => head[i] === b);
}

// ...inside the handler, after the reason is validated:
let attachmentKey: string | null = null;
let attachmentFilename: string | null = null;
const file = form.get("attachment");
if (file instanceof File && file.size > 0) {
  if (file.size > PDF_MAX_BYTES) {
    return NextResponse.json({ error: "Attachment must be 2MB or smaller" }, { status: 400 });
  }
  const buf = await file.arrayBuffer();
  if (!(await isPdf(buf))) {
    return NextResponse.json({ error: "Attachment must be a valid PDF file" }, { status: 400 });
  }
  const requestedAt = Date.now();
  attachmentKey = `unlock-requests/${district.id}/${requestedAt}.pdf`;
  attachmentFilename = file.name.slice(0, 200);
  const { env } = getCloudflareContext();
  await env.ATTACHMENTS.put(attachmentKey, buf, { httpMetadata: { contentType: "application/pdf" } });
}
```

Magic bytes (not the client-reported `Content-Type`) and size are both re-checked here — nothing
about re-enabling the frontend input changes this route's zero-trust posture.

## What actually needs to happen

storage, 1M Class A / 10M Class B ops per month, $0 egress). At this app's scale — max 75

## Why R2 over the alternatives (for context, not action)

- **D1 as a BLOB column** — rejected. D1 caps any single BLOB/row at 2,000,000 bytes, right at
  this feature's 2MB cap, and a scanned letter (image-based PDF) can realistically exceed that.
- **Workers KV** — not evaluated in depth; could be worth a look if R2 turns out to be
  unworkable for non-technical reasons (KV's per-value limit is 25MB, well within budget), but
  R2 was already fully built and is Cloudflare's purpose-built object storage, so it stayed the
  first choice once enabling it is possible.
- **A third-party storage provider** (Backblaze B2, Supabase Storage, etc.) — rejected as a new
  external dependency/vendor for a 150MB-max, single-purpose use case when the existing
  Cloudflare account (already hosting D1 and both Workers/Pages deployments) can do it natively.
